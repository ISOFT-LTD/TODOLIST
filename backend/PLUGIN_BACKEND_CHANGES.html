Todo Plugin Backend Changes

Reference for the Todo export provider and the create-todo notification header introduced in backend/main.py.

Overview Export route Processing flow Security Limits Notification header Operations

Overview

New provider endpoint

GET /api/exports/todos returns structured Todo data to Core.

Core owns file generation

The plugin returns JSON. Core's existing Celery worker creates CSV or XLSX files.

Delegated authorization

The route requires the todo.view action from Core's delegated JWT.

Create notification

A successful Todo creation now returns X-Cobalt-Admin-Notification.

Key boundary: the Todo plugin does not connect to Redis, does not register Celery tasks, and does not write export files. It only supplies a bounded data document to trusted Core.

MethodGET

Implementation

@exports_router.get("/todos")
def export_todos(who=Depends(require_delegated_action(READ_TODO))):
    todos = models.list_todos(*owner_of(who))
    return {
        "filename": "todos",
        "columns": ["id", "title", "done", "computer_id"],
        "rows": [
            [todo.id, todo.title, todo.done, todo.computer_id]
            for todo in todos
        ],
    }

Response contract

FieldMeaning
filename Safe base name used by Core when the generated file is downloaded.
columns Ordered spreadsheet and CSV header names.
rows Ordered scalar values. Every row must contain one value per column.

Export processing flow

Step 1 The plugin UI posts an export request to Core.
Step 2 Core verifies the browser session and application access.
Step 3 Core calls /api/exports/todos with delegated identity.
Step 4 Core validates the document and queues its shared export task.
Step 5 The UI polls Core and downloads the generated XLSX file.

Core request used by the frontend

POST /export/plugins/todo
Content-Type: application/json

{
  "path": "/api/exports/todos",
  "format": "xlsx"
}

The route above belongs to Core, not the Todo backend. Core uses the supplied application-relative path to fetch the export document and sends the validated rows to export_plugin_data_task on the existing exports Celery queue.

Authorization and data isolation

  1. require_delegated_action(READ_TODO) rejects calls without a valid Core-issued token containing todo.view.
  2. owner_of(who) derives the tenant and subject from the verified delegated principal.
  3. models.list_todos(...) reads only records belonging to that tenant and subject.
  4. The browser never receives or forwards Core's delegated JWT. Core creates it server-side for the application call.
Do not make the provider route public and do not replace owner_of(who) with a client-supplied user identifier. Either change would break the export's authorization boundary.

Core validation limits

Core validates the plugin response before placing it on the worker queue. The Todo response must remain within these limits.

Document size

Maximum 5 MiB.

Columns

Between 1 and 100.

Rows

Maximum 10,000.

Names

Filename and column names are limited to 120 characters.

String cells

Maximum 32,767 characters.

Cell types

String, number, boolean, or null only.

Core also requires equal-width rows, supports only csv and xlsx, and neutralizes spreadsheet formula prefixes before writing any cell.

Create-Todo notification header

The existing POST /api/todos route now accepts FastAPI's Response object, creates the Todo normally, and adds this response header: 

X-Cobalt-Admin-Notification: todo_created
@todos_router.post("", response_model=TodoOut, status_code=201)
def create_todo(todo: TodoCreate, response: Response, who=...):
    created = models.create_todo(
        *owner_of(who), todo.title, computer_id=todo.computer_id
    )
    response.headers["X-Cobalt-Admin-Notification"] = "todo_created"
    return created

The response body and the todo.create authorization rule are unchanged. The header is metadata that Core can use to refresh or display administrative notifications.

Operational checklist

  • Deploy the updated Todo backend before enabling the frontend export button.
  • Deploy the Core export route and worker task on every Core instance.
  • Ensure a worker consumes the existing exports queue.
  • Grant users read access to the Todo application and the todo.view action.
  • Keep the plugin response below Core's documented validation limits.
  • Use Core's status and download routes; do not expose plugin storage or worker credentials.
